# Castor A candidate: conformance and code tour

This page records bounded evidence for the Castor A candidate, not a release acceptance. The supported candidate is `castor-client` 0.7.0a1 talking to the Rust `castord` D1 host. The old `castor-kernel` 0.6 wheel remains a historical Python engine and is not part of this candidate.

## Authority path

`packages/castor-client/src/castor_client/session.py` limits Agent and operator requests before transport, opens a fresh connection per request, and surfaces transport or gateway failures without local fallback or automatic effect retry. `client.py` owns the framed AISA request and response correlation. `tests/dogfood/ring3_agent.py` is the Python guest; it uses `AgentSession` on the Roche-mounted Agent socket. The Rust host in `kernel/src/bin/castord.rs` enforces the physical channel split. The trusted actuator and evidence service use separate host channels.

The code and test candidate with all four Grok-review corrections passed [Castor PR #10 CI run 36099030458](https://github.com/substratum-labs/castor/actions/runs/36099030458) at `d9ba761`: seven jobs succeeded, including Python 3.11/3.12/3.13, lint, kernel, Paper A smoke and `roche-a`. The Linux `roche-a` job passed seven physical tests covering normal and C1/C2/C3/D1/H1 cases. Local macOS Docker Desktop cannot project the host Unix socket into its Linux VM, so the Linux runner is the Roche physical oracle. Current PR #11 evidence appears below; no release, merge or publication is implied.

The release gate must also decide how to retire the old `castor-kernel` distribution. Both Tiphys and castor-server depend on `castor-kernel>=0.5.1` and import its Python authority modules; a higher-version shim would satisfy those ranges and break them. The conservative candidate keeps `castor-kernel` frozen and distributes `castor-client` separately until those consumers migrate or pin an upper bound. The candidate `publish.yml` now recognizes only `client-v*` tags, builds and audits only the client artifacts, and leaves PyPI upload disabled unless the separately controlled `CASTOR_CLIENT_PUBLISH_ENABLED` variable is set. No release tag or publication has occurred.

The candidate now exports an operation-specific request class for every current Agent and operator D1 opcode in `operations.py`, with typed nested action bindings, query descriptors and capability grants. `outcomes.py` describes the corresponding Rust response shapes, and `AisaResponse` carries those types through `send()` for static callers. The generic request envelopes and low-level transport remain available. The client validates transport/shape and channel role; Rust `castord` still validates D1 semantics. A RED→GREEN test caught the required omission of an absent `RequestInteraction.descriptor`, which Rust otherwise rejects when sent as `null`.

On the isolated completion candidate, the built `castor-client` wheel includes `operations.py`, `outcomes.py` and `py.typed` with no legacy `castor` module. Local verification: client unit suite 23/23 on each supported Python 3.11, 3.12 and 3.13; Castor A physical suite 9/9 plus six subtests; full Python suite 642 passed/16 skipped/83 subtests; full Rust kernel tests including 13 Roche sandbox contract tests; Cargo clippy with warnings denied, scoped Ruff check/format, and strict MkDocs build. An agy reviewer caught a Python 3.11–3.13 `dataclass(slots=True)`/zero-argument `super()` runtime failure in the new `RequestInteraction` path that the original CI missed because it ran only root `tests/`. Commit `c6f931d` uses an explicit base-class call, makes the CI Python matrix select its intended interpreter, and adds the client unit suite to each matrix job. [CI run 36156978026](https://github.com/substratum-labs/castor/actions/runs/36156978026) passed all seven jobs on that code commit, including Linux `roche-a` and Python 3.11/3.12/3.13. The macOS Python Roche cases remain Linux-gated; formal reviewer closure and Yong's release decision remain required before a tag or publication.
